# Decision Log

This document records every non-trivial documentation decision made for the `hello_world` project — what was decided, the alternatives considered, the rationale for the choice, and the risks it carries. Per the project's **Explainability** rule (Rule 1), this decision log is the single source of truth for *why*: rationale is captured here and is intentionally **not** duplicated in code comments, JSDoc, or the `README.md` body.

| Decision | Alternatives Considered | Rationale | Risks |
|---|---|---|---|
| Overwrite `README.md` with comprehensive documentation despite its "Do not touch!" note (in the original pre-overwrite README stub — baseline commit 6114a2b, README.md:1-2). | Leave the two-line stub untouched; create a separate docs file and keep the stub. | The user explicitly requested a comprehensive README; the "Do not touch!" line is a stale placeholder that conflicts with the request, and `README.md` is the conventional project entry point. Prior content is preserved in version control. | The note may have signaled an intent to preserve the file; mitigated because the explicit current requirement supersedes the stale note. |
| Present a single, consistent project name `hello_world`, reconciling it against the old README title `hao-backprop-test` (in the original pre-overwrite README stub — baseline commit 6114a2b, README.md:1). | Keep the old README title `hao-backprop-test`; present both names side by side. | `package.json` is the authoritative manifest and declares the name `hello_world` (package.json:2); a single consistent name prevents confusion. | Any external reference to `hao-backprop-test` becomes inconsistent; low impact for a local test project. |
| Prescribe `node server.js` as the documented run command. | `npm start`; `node index.js` (per the `main` field). | No `start` script exists (package.json:6-8) and `index.js` is absent (package.json:5); `server.js` is the only runnable entry point (server.js:28-42). | Users following the `main` field may be confused; mitigated by explicitly disclosing the discrepancy in the README. |
| Place this decision log at the repository root as `DECISIONS.md` rather than under a `docs/` tree. | Create a `docs/` directory; embed the decisions inside the README. | The project is a single-file app in a flat repository; a `docs/` tree would be over-engineering and would violate the minimal-changes rule, whereas a root-level file is easily discoverable. | If the project grows, a `docs/` structure may later be preferable; migration is trivial. |
| Document the anonymous arrow-function callbacks in `server.js` with JSDoc rather than refactoring them into named functions. | Refactor the callbacks into named functions to make them easier to annotate; skip JSDoc entirely. | The user asked for JSDoc on the functions; descriptive JSDoc can be attached above the anonymous callbacks without altering code, honoring the minimal-changes rule — refactoring to named functions would change structure and logic (server.js:28-32, server.js:40-42). | JSDoc on anonymous callbacks is marginally less conventional than on named functions; acceptable and standard-compliant. |
| Leave `package.json` and `package-lock.json` unmodified. | Add a `start` script; add an `engines` field; fix the dangling `main` field. | Rule 3 (minimal changes) confines edits to documentation; editing the manifest would be an out-of-scope code change. | The manifest keeps a dangling `main: index.js` (package.json:5); mitigated by documenting the discrepancy rather than fixing it. |
| Disclose that automated tests are not configured. | Add a test suite; omit the topic entirely; fabricate test instructions. | The `test` script intentionally fails (package.json:7) and adding tests is out of scope; honest disclosure avoids misleading users. | Readers may expect tests; mitigated by a clear statement and an out-of-scope note in the README. |
| Document the `127.0.0.1` loopback deployment caveat. | Omit the caveat; change the bind address to `0.0.0.0`. | The server binds to loopback (server.js:12); changing it would be an out-of-scope logic change, so the limitation is documented along with workarounds (a reverse proxy, or editing `server.js`). | Users may still attempt remote access and fail; mitigated by a prominent caveat in the README Deployment section. |
| Embed Mermaid diagrams directly in Markdown and hand-author the documentation instead of adopting a documentation generator or installing JSDoc tooling. | Install `jsdoc@4.0.5` to generate browsable HTML API docs; stand up a `docs/` site generator (MkDocs, Docusaurus, or Sphinx). | Common hosts render Mermaid natively with no build step, and the project is a small single-file server (server.js:1-42), so a generator would be over-engineering and would add unwanted dependencies (Rule 3). HTML API-doc generation is recorded as an optional route only. | Mermaid requires a compatible viewer to render; mitigated because the diagram source remains readable as plain text and the diagrams are simple. |
| Cite the source file and line (for example, `server.js:28-32`) for every technical claim across the documentation. | Omit citations; cite files without line numbers. | Line-level citations make each claim traceable and verifiable against the code, supporting the accuracy and maintainability targets. | Citations can drift if the code is later edited; mitigated because the referenced constructs are stable and the documentation notes it must be kept in sync with the code. |
| Treat the unrelated polyglot fixtures (`LoginTest.java`, `industry.csv`, `test.py.txt`, `test.txt.txt`, `100Pages.pdf`, `demo.jpg`, `sample.doc`) as out of scope and label them as non-application test fixtures in the README Project Structure section. | Document each fixture in detail; delete the fixtures from the repository. | These files carry no runtime behavior and are unreferenced by `server.js` (server.js:1-42); documenting or deleting them would exceed the documentation scope (Rule 3). | Readers may wonder why the files exist; mitigated by a one-line note clarifying they are unrelated fixtures. |
| Document the standard HTTP `HEAD` semantics (a `HEAD` response carries no message body) in the README API section, rather than modifying `server.js` to force a body or `Content-Length` onto `HEAD` responses. | Add `HEAD`-specific logic to the request handler so `HEAD` returns a body and `Content-Length`; leave the README "any method" claim unqualified. | The HTTP specification requires that a response to a `HEAD` request contain no message body, and the Node.js core `http` runtime already enforces this by omitting the body — and the `Content-Length` derived from it — for `HEAD` (server.js:28-32); adding handler logic would change executable behavior, violating the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2) and contradicting the HTTP specification, so the exception is documented instead to keep the docs accurate against the running server. | The README "any method" summary is qualified for `HEAD`; mitigated by a precise note in the API Documentation section and this decision entry. |
| Document the two Node.js parser-level exceptions to the "any method / any path" contract — an unrecognized or wrong-case method token receives a bare `400`, and a request line plus headers larger than `http.maxHeaderSize` receives `431` — in a README API subsection, rather than modifying `server.js`. | Add method-token validation and request-size handling to the request handler so that every request reaches it and receives `200`; leave the absolute "every request, any method, any path" claim in the README unqualified. | Both rejections are produced inside the Node.js HTTP parser before the request listener is invoked (server.js:28-32), so no application-level change could alter them, and adding handler logic would change executable behavior — forbidden by the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2); documentation must match the running server, so the two exceptions are documented with their exact observed responses instead. | Readers may still expect literal universality from the `ANY` / `/*` endpoint row; mitigated by the Platform-Level Exceptions table, which states each exact response, that the handler is never invoked, and the request sizes that still return `200`. |
| Keep the request-lifecycle Mermaid diagram verbatim as specified — including its `Any request (any method, any path)` label — and carry the parser-level qualification in an adjacent caption and the Platform-Level Exceptions table. | Edit the diagram label to name the parser-accepted subset; extend the sequence diagram with rejection branches for the `400` and `431` cases. | The diagram's content is specified verbatim by the Agent Action Plan (AAP §0.4.3), which takes precedence, and a one-line caption plus the neighbouring exceptions table conveys the same accuracy without altering specified content, enlarging the diagram, or restating the endpoint contract (server.js:28-32). | A reader who views only the diagram may generalize its "any method, any path" label; mitigated by the caption placed directly beneath the diagram, which points to the exceptions subsection. |
