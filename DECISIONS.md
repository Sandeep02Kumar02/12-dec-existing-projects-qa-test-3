# Decision Log

This document records every non-trivial documentation decision made for the `hello_world` project — what was decided, the alternatives considered, the rationale for the choice, and the risks it carries. Per the project's **Explainability** rule (Rule 1), this decision log is the single source of truth for *why*: rationale is captured here and is intentionally **not** duplicated in code comments, JSDoc, or the `README.md` body.

| Decision | Alternatives Considered | Rationale | Risks |
|---|---|---|---|
| Overwrite `README.md` with comprehensive documentation despite its "Do not touch!" note (in the original pre-overwrite README stub — baseline commit 6114a2b, README.md:1-2). | Leave the two-line stub untouched; create a separate docs file and keep the stub. | The user explicitly requested a comprehensive README; the "Do not touch!" line is a stale placeholder that conflicts with the request, and `README.md` is the conventional project entry point. Prior content is preserved in version control. | The note may have signaled an intent to preserve the file; mitigated because the explicit current requirement supersedes the stale note. |
| Present a single, consistent project name `hello_world`, reconciling it against the old README title `hao-backprop-test` (in the original pre-overwrite README stub — baseline commit 6114a2b, README.md:1). | Keep the old README title `hao-backprop-test`; present both names side by side. | `package.json` is the authoritative manifest and declares the name `hello_world` (package.json:2); a single consistent name prevents confusion. | Any external reference to `hao-backprop-test` becomes inconsistent; low impact for a local test project. |
| Prescribe `node server.js` as the documented run command. | `npm start`; `node index.js` (per the `main` field). | No `start` script exists (package.json:6-8) and `index.js` is absent (package.json:5); `server.js` is the only runnable entry point (server.js:28-42). | Users following the `main` field may be confused; mitigated by explicitly disclosing the discrepancy in the README. |
| Place this decision log at the repository root as `DECISIONS.md` rather than under a `docs/` tree. | Create a `docs/` directory; embed the decisions inside the README. | The project is a single-file app in a flat repository; a `docs/` tree would be over-engineering and would violate the minimal-changes rule, whereas a root-level file is easily discoverable. | If the project grows, a `docs/` structure may later be preferable; migration is trivial. |
| Document the anonymous arrow-function callbacks in `server.js` with JSDoc rather than refactoring them into named functions. | Refactor the callbacks into named functions to make them easier to annotate; skip JSDoc entirely. | The user asked for JSDoc on the functions; descriptive JSDoc can be attached above the anonymous callbacks without altering code, honoring the minimal-changes rule — refactoring to named functions would change structure and logic (server.js:28-32, server.js:40-42). | JSDoc on anonymous callbacks is marginally less conventional than on named functions; acceptable and standard-compliant. |
| Leave `package.json` and `package-lock.json` unmodified. | Add a `start` script; add an `engines` field; fix the dangling `main` field. | Rule 3 (minimal changes) confines edits to documentation; editing the manifest would be an out-of-scope code change. | The manifest keeps a dangling `main: index.js` (package.json:5); mitigated by documenting the discrepancy rather than fixing it. |
| Disclose that automated tests are not configured. | Add a test suite; omit the topic entirely; fabricate test instructions. | The `test` script intentionally fails (package.json:7) and adding tests is out of scope; honest disclosure avoids misleading users. | Readers may expect tests; mitigated by a clear statement and an out-of-scope note in the README. |
| Document the `127.0.0.1` loopback deployment caveat, including the container published-port case. | Omit the caveat; change the bind address to `0.0.0.0`. | The server binds to loopback (server.js:12); changing it would be an out-of-scope logic change, so the limitation is documented along with workarounds (a reverse proxy, or editing `server.js`). The same bind applies inside a container, so a published port (`docker run -p 3000:3000`) is forwarded to the container's own interface and refused by a loopback listener; that case is therefore documented in the caveat as well, rather than fixed by changing the bind host, which would be the same executable change. | Users may still attempt remote access and fail, and a reader publishing a container port sees a refused connection or an empty reply until the bind host is changed; mitigated by a prominent caveat in the README Deployment section that names both the remote-host and the container case. |
| Embed Mermaid diagrams directly in Markdown and hand-author the documentation instead of adopting a documentation generator or installing JSDoc tooling. | Install `jsdoc@4.0.5` to generate browsable HTML API docs; stand up a `docs/` site generator (MkDocs, Docusaurus, or Sphinx). | Common hosts render Mermaid natively with no build step, and the project is a small single-file server (server.js:1-42), so a generator would be over-engineering and would add unwanted dependencies (Rule 3). HTML API-doc generation is recorded as an optional route only. | Mermaid requires a compatible viewer to render; mitigated because the diagram source remains readable as plain text and the diagrams are simple. |
| Cite the source file and line (for example, `server.js:28-32`) for every technical claim across the documentation. | Omit citations; cite files without line numbers. | Line-level citations make each claim traceable and verifiable against the code, supporting the accuracy and maintainability targets. | Citations can drift if the code is later edited; mitigated because the referenced constructs are stable and the documentation notes it must be kept in sync with the code. |
| Treat the unrelated polyglot fixtures (`LoginTest.java`, `industry.csv`, `test.py.txt`, `test.txt.txt`, `100Pages.pdf`, `demo.jpg`, `sample.doc`) as out of scope and label them as non-application test fixtures in the README Project Structure section. | Document each fixture in detail; delete the fixtures from the repository. | These files carry no runtime behavior and are unreferenced by `server.js` (server.js:1-42); documenting or deleting them would exceed the documentation scope (Rule 3). | Readers may wonder why the files exist; mitigated by a one-line note clarifying they are unrelated fixtures. |
| Document the standard HTTP `HEAD` semantics (a `HEAD` response carries no message body) in the README API section, rather than modifying `server.js` to force a body or `Content-Length` onto `HEAD` responses. | Add `HEAD`-specific logic to the request handler so `HEAD` returns a body and `Content-Length`; leave the README "any method" claim unqualified. | RFC 9110 §9.3.2 (https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2) states that a server MUST NOT send content in a response to a `HEAD` request, and the Node.js 22.x `http` documentation (https://nodejs.org/docs/latest-v22.x/api/http.html#responsewritechunk-encoding-callback) documents that writing a body is not allowed for a `HEAD` request — the write is rejected with `ERR_HTTP_BODY_NOT_ALLOWED` only when `rejectNonStandardBodyWrites` is enabled, which this server does not do, so the body, and the `Content-Length` that would be derived from it, are simply not sent; `server.js:28-32` is cited only for what those lines contain, namely a handler that calls `res.end('Hello, World!\n')` unconditionally with no `HEAD`-specific branch. Adding such a branch would change executable behavior, violating the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2) and contradicting the HTTP specification, so the exception is documented instead to keep the docs accurate against the running server. | The README "any method" summary is qualified for `HEAD`; mitigated by a precise note in the API Documentation section (README.md:88) and this decision entry. |
| Leave the two Node.js runtime-level *rejections* of the "any method / any path" contract — an unrecognized or wrong-case method token answered `400 Bad Request`, and a request line plus headers larger than the 16 KiB header ceiling answered `431 Request Header Fields Too Large` — to the Node.js runtime, adding no method-token validation, no header-size configuration and no `clientError` handler to `server.js`; the third runtime-level departure, a `CONNECT` request, is recorded in the row below. | Add method-token validation and request-size handling to the request handler so that every request reaches it and receives `200`; register a `server.on('clientError', …)` handler or pass `http.createServer({ maxHeaderSize })` to reshape the two responses. | Both requests are rejected by the Node.js HTTP parser before the `request` event, so this server's request listener is never invoked, and Node's own default `'clientError'` handling answers them — closing the socket with `400 Bad Request`, or with `431 Request Header Fields Too Large` for an `HPE_HEADER_OVERFLOW` error (https://nodejs.org/docs/latest-v22.x/api/http.html#event-clienterror), and the ceiling itself is `http.maxHeaderSize`, 16384 bytes (16 KiB) by default (https://nodejs.org/docs/latest-v22.x/api/http.html#httpmaxheadersize), overridable per server through the `maxHeaderSize` option (https://nodejs.org/docs/latest-v22.x/api/http.html#httpcreateserveroptions-requestlistener). Altering either response would therefore require a `clientError` handler or server/parser configuration — executable changes this documentation effort deliberately does not make, because the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2) forbid changing behavior; `server.js:28-32` is cited only for what those lines contain, namely a single request listener that inspects nothing and returns a constant response, with no `clientError` handler and no `maxHeaderSize` option anywhere in the file. | The README endpoint summary reads as absolute, so a reader may expect literally every request to reach the handler; the residual gap is a documentation-accuracy risk in the endpoint contract — closed where that contract is written rather than here — and not a behavioral one, since the server's code is unchanged. |
| Document the `CONNECT` case in the README endpoint contract rather than registering a `'connect'` handler in `server.js`. | Register `server.on('connect', …)` to answer or tunnel `CONNECT` requests; omit the case from the documented contract. | Node's HTTP parser routes a `CONNECT` request line to the server's `'connect'` event rather than to `'request'` before any application listener runs (https://nodejs.org/docs/latest-v22.x/api/http.html#event-connect_1), and with no `'connect'` listener registered Node destroys the socket, so the client receives zero bytes rather than an HTTP response; `server.js:28-32` holds a single `request` listener that inspects nothing and `server.js:1-42` registers no other event handler, so making `CONNECT` reach the handler would mean adding an executable listener — a behavior change the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2) forbid — therefore the runtime's own behavior is documented instead. | A reader may expect `CONNECT` to reach the handler and receive `200`, and a proxy client probing with `CONNECT` sees a closed connection rather than an HTTP error; mitigated by naming the case, its zero-byte close and the absent `'connect'` handler in the README endpoint contract. |
| Document that an upgrade request (`Connection: Upgrade` with, for example, `Upgrade: websocket`) is not intercepted and receives the same `200` response as any other request, rather than registering an `'upgrade'` handler in `server.js`. | Register `server.on('upgrade', …)` to complete or reject the handshake; say nothing about upgrade requests. | Node dispatches an upgrade request to the `request` event when the server has no `'upgrade'` listener (https://nodejs.org/docs/latest-v22.x/api/http.html#event-upgrade_1), so the request falls through to the single request listener at `server.js:28-32` and is answered `200` with the constant body; `server.js:1-42` registers no `'upgrade'` listener, and adding one would be an executable change barred by the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2), so the runtime's fall-through behavior is documented instead. | Readers familiar with WebSocket servers may assume a handshake is handled; mitigated by stating the behavior explicitly in the README API Documentation exceptions subsection alongside the intercepted cases. |
| Document the full boot-persistence path in the README Deployment section — `pm2 startup` and the root command it prints, run before `pm2 save`, plus `systemctl daemon-reload` followed by `systemctl enable --now` for the unit — and keep the section's reboot-survival promise, stating it as conditional on the boot hook being installed. | Narrow the promise to crash restarts only and merely point at `pm2 startup`; drop the pm2 example altogether. | `pm2 save` alone only writes the process list to `~/.pm2/dump.pm2`, and nothing restarts pm2 after a reboot until the init-system hook that `pm2 startup` generates has been installed (https://pm2.keymetrics.io/docs/usage/startup/), so the shorter snippet did not deliver the outcome the section promised; documenting the missing steps keeps the guidance achievable while remaining documentation-only, whereas narrowing the promise would drop durable operation, which is exactly what the deployment requirement asks the section to cover. | The exact root command `pm2 startup` prints varies by init system, pm2 version and user, so the README names the step rather than a literal command, and a reader on a host without systemd or upstart must consult the pm2 documentation. |
| Narrow the Dockerfile sketch's `COPY` in the README Deployment section to the application files (`server.js`, `package.json`, `package-lock.json`) and state that broadening it requires a `.dockerignore`, rather than adding a `.dockerignore` to the repository. | Create a real `.dockerignore` excluding the unrelated fixtures and `.git`; keep `COPY . .` and warn in prose only. | The repository root also holds the unrelated fixtures, about 11.7 MB in total, in addition to the `.git` history, with no `.dockerignore` or `.gitignore` to filter them, so `COPY . .` would ship all of it in the image and contradict the README's own Project Structure section, which labels those files as no part of the application; adding the file would create a deliverable outside the documentation scope this effort is confined to (AAP §0.8.2, Rule 3), while narrowing the sketch fixes the guidance with no new file. | A reader who later adds application files must extend the `COPY` list; noted where the sketch is documented. |
| Show `WorkingDirectory=`, `User=`, `Group=` and `NoNewPrivileges=true` in the README Deployment section's systemd unit sketch and tell the reader to create the unprivileged account. | Leave the minimal unit as it was, which runs the service as `root`; add a full hardening stanza (`ProtectSystem`, `PrivateTmp`, `ProtectHome`, and so on). | A `[Service]` stanza with no `User=` runs as `root`, and the server needs no elevated privileges because its port `3000` is outside the privileged range below 1024 (server.js:17), so a dedicated unprivileged account is the smallest change that removes that privilege from copied-and-pasted guidance, whereas a full hardening stanza would obscure a sketch whose purpose is to show the run command. | The account name and the `/path/to` prefix are values the reader must substitute for their own host, and the sketch is a starting point rather than a complete hardening baseline. |
| Document the protocol-version-dependent framing of the 14-byte response body in the README API Documentation section — `Content-Length: 14` on an HTTP/1.1 response and no `Content-Length` header at all on an HTTP/1.0 response — rather than setting an explicit `Content-Length` header in `server.js`. | Add `res.setHeader('Content-Length', Buffer.byteLength('Hello, World!\n'))` to the request handler so every response carries the header regardless of the client's protocol version; drop the `Content-Length: 14` figure from the README and document only status, content type and body; leave the blanket claim that every method other than `HEAD` returns the body with `Content-Length: 14`. | The handler calls `res.end('Hello, World!\n')` and sets only `Content-Type` (server.js:28-32), so the Node.js `http` runtime chooses the framing per request: an HTTP/1.1 response carries a runtime-computed `Content-Length: 14` whether the connection is kept alive or closed, whereas an HTTP/1.0 response — which cannot use chunked transfer coding, and which Node closes even when the client asks for keep-alive — is delimited by connection close and carries no `Content-Length`, its body length being the octets received before that close (RFC 9112 §6.3, https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3). The header is therefore a property of the client's protocol version rather than of its method, and setting it in code would be an executable change barred by the minimal-changes rule (Rule 3) and the out-of-scope boundary (AAP §0.8.2), while dropping the figure would lose response-shape accuracy that the AAP §0.7.2 accuracy criterion requires — so both cases are stated as fact in the documentation instead. | A reader skimming the HTTP/1.1 `curl -i` example may still assume the header is unconditional; mitigated by naming the HTTP/1.0 case, and giving the `curl --http1.0 -i http://127.0.0.1:3000/` command that reproduces it, at README.md:88 and README.md:111. |
